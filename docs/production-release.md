# 正式版本发布

GitHub Actions 只保留 **CI** 和 **发布正式版本**。用户在「发布正式版本」点击 **Run workflow**、选择 `main`；代码提交和 CI 成功不会自动发布生产。

Workflow 的 `operation` 默认为 `release`，执行下文正式发布。`cache-inspect`、`cache-clean`、`images-inspect`、`images-clean`、`retired-containers-inspect` 和 `retired-containers-clean` 是独立的生产维护模式，复用同一 production 凭据与发布锁，不创建标签或 Release，也不切换应用或执行迁移。

## 生产缓存维护

维护候选先取得精确主分支 CI，再经既有受限入口更新五项固定工具。旧工具更新协议要求源码版本前进，因此工具候选可以高于线上应用版本；只更新工具时，线上 checkout、发布回执与应用版本保持原值。

先用 `cache-inspect` 读取 default builder 的缓存记录，按共享/私有及可回收/受保护四类统计。报告只包含安全的记录元数据和资源保护摘要，不输出构建命令描述、环境变量或密钥。检查在 root 私有路径保存 15 分钟有效的计划，绑定线上版本、工具版本与资源快照。

`cache-clean` 会先重新检查，再按同一份短期计划清理精确的、仍可回收的记录 ID；不纳入新记录，不清理变为占用中或已变化的记录。清理前、每批后及结束时核对当前/上一版本镜像、所有既有容器和数据卷、配置、数据库账本与应用健康，漂移时停止后续删除。不执行全局缓存清理、镜像删除、容器或卷清理。

维护产物为 `production-cache-maintenance`，包含四类记录大小、实际删除/剩余 ID、文件系统可用空间净变化和保护校验。共享缓存可能只移除元数据，其记录大小不能等同于磁盘释放量；受保护记录保留，不为满足总量数字删除在用层。

缓存维护结束会再读取一次 default builder，生成 `budget.json` 与 `budget.md`，同步到 Actions Summary：目标为 **2,000,000,000 bytes（2 GB）**。报告区分不可回收和仍可回收的大小，逐项说明在用、新出现、属性变化或引擎保留等原因。共享标记单独说明，不将共享记录全部视为受保护，也不推断它属于某个具体镜像。估算读数标为 `estimated`，不能确认精确达标；检查或保护核验失败标为 `unverified`。

带项目标题但归属标签不完整或不匹配的历史镜像作为额外保护记录保存 ID 与元数据哈希，报告仅输出固定原因码。它们不满足当前或上一版本的身份要求；清理中这些保护记录发生变化同样停止后续删除。

## 已授权历史镜像维护

`images-inspect` 只盘点源码中冻结的 17 个历史镜像 ID，输出版本、服务、归属证据、已识别镜像引用和全部容器引用（含已停止容器）。本地 Compose 名称及其 `docker.io/library/` 规范形式、明确的项目 GHCR 仓库分别按精确白名单核对；未知来源或引用仅输出固定原因和哈希并保留，不输出环境变量、任意标签或构建历史。

经历史部署源码和线上引用哈希逐项匹配的旧 v1 发布仓库及 `0.5.0-dev.1` 回滚镜像，按固定 ID、版本、服务和完整 tag/digest 设置精确例外；不放宽仓库前缀或接受其他标签。容器引用保护仍优先。

`images-clean` 先重新盘点并生成 15 分钟 root 私有计划，仅处理归属确认、严格早于上一版本、无任何容器引用且不属于当前/上一版本的固定范围镜像。每次删除前后核对所有镜像 ID、容器及状态、数据卷、配置、数据库账本和健康，漂移即停止。只用完整不可变 ID 执行非强制 `image rm --no-prune`，不清理父镜像，不回退到标签删除或强制删除；引擎拒绝的镜像保留并报告。新出现或变化的记录不会追加到计划。

产物 `production-image-maintenance` 保存检查与清理 JSON、逐项保留原因、实际移除 ID、保护证明、公网健康和文件系统可用空间净变化。镜像标称大小包含共享层，不能直接视为释放空间。维护结束删除 Runner 临时 SSH 身份；业务数据、上传文件、历史备份、容器和数据卷不清理。

## 指定旧版停止容器维护

`retired-containers-inspect`、`retired-containers-clean` 仅接受源码中冻结的两个 `0.8.0-dev.4` 容器：旧 Prisma 迁移任务与数据库角色校准任务。检查固定容器/镜像 ID、项目/服务/版本标签、源码定义的完整命令、非特权用户、成功退出与停止时间、禁止重启、空挂载、其他容器依赖及可写层变化。未知文件路径只报告数量和哈希；出现非临时文件变化、挂载、依赖或身份不明时保留。目标容器的用途诊断模板不读取 Env、容器日志或文件内容。

清理使用 15 分钟 root 私有计划和现有生产锁，每次重新核对全部容器、镜像、卷、配置、当前/上一版本及数据库账本。仅对固定容器 ID 使用非强制 `docker container rm`，不带删除卷参数，不停止或重启任何容器，不使用 prune，不清理镜像或业务数据。只允许相应的已验证容器记录从快照消失；其他变化立即停止。后续镜像删除通过既有 `images-clean` 单独串行执行，重新确认无容器引用后才处理对应历史镜像。产物 `production-retired-container-maintenance` 记录用途、检查、实际删除、磁盘变化和资源保护；维护结束清理 Runner 临时 SSH 身份。

## 日常发布

1. 将改动、递增的 `MAJOR.MINOR.PATCH` 版本及对应说明提交到 `main`。
2. CI 按当前生产源版本到该 SHA 的累计差异生成受影响检查清单，构建一次共享镜像图，使用同一镜像验证选中的浏览器用例、性能与必要的隔离候选，然后发布不可变摘要镜像和 `release-images` 清单。
3. 点击「发布正式版本」。工作流核对精确 SHA 的成功 CI 及实际源版本证明，创建或复用 annotated 版本标签；生产作业再更新固定发布工具。
4. 生产校验 CI 运行、产物哈希、镜像摘要/ID、版本和源码 SHA，拉取已验证镜像，不构建源码。迁移清单未变时跳过迁移和权限协调；变化时执行已经 CI 验证的迁移。
5. 自动核对应用、Worker、数据库账本和公网健康。成功后写发布回执、安全清理旧镜像，再检查缓存；超过 2 GB 时冻结计划并清理精确可回收 ID，随后重新检查并保存报告，最后发布 GitHub Release。

常规发布不创建或验证备份，不执行恢复演练。已有业务数据、数据卷、上传文件和历史备份保留。新回执使用 `release_protocol=stable-v2-images`、`backup=not-required restore=not-required`；历史回执继续兼容。

版本标签不可移动，必须为 annotated 且指向本次相同 SHA。主分支前进、生产来源改变、CI 证明不足或镜像清单过期时，发布会在切换前停止。重新运行精确提交的主分支 CI 后再点击发布，不重复标签全套测试。CI 产物保留 30 天。

## 受影响检查

源码作业与镜像作业会独立生成同一份检查计划，绑定生产源提交、候选 SHA、风险和计划指纹。通过 TypeScript 反向依赖与[路由覆盖注册表](../config/ci-test-coverage.json)选择相关单元合同和浏览器文件；变更的用例本身也会纳入。两个作业的计划指纹与执行回执必须匹配，才生成既有主分支 CI 证明。

| 变更 | 执行范围 |
| --- | --- |
| 局部客户端组件、样式 | 相关 unit 合同和映射的浏览器、无障碍用例；保留 Lint、类型、构建与性能检查 |
| 共享用户侧栏 | `feedback-layout-parity`、`short-page-scroll`、`user-shell-navigation` 三个 spec，覆盖布局、滚动和真实项目切换 |
| 文档、已验证的纯版本元数据 | 无浏览器影响时不启动浏览器；版本变化仍核对发布身份合同 |
| 服务端、安全、迁移、依赖、未知影响 | 保留全量 unit 覆盖率及适用的数据库门禁；不能证明浏览器覆盖时回退全量 |
| 全局布局、选测策略、运行器或共享夹具 | 回退全量浏览器，验证选择器本身和跨页面影响 |

纯 UI 不再重复服务端全套 unit 覆盖率、无关数据库业务门禁或 Compose 候选。发布基础设施仍执行发布合同和同镜像候选。`ci-source-checks` 与 `ci-browser-checks` 产物保存清单、原因、文件数量和执行回执，摘要显示选集规模。

浏览器执行前会用 Playwright 发现实际用例并核对精确文件集，执行后核对结果；缺失文件、零用例、全部跳过或计划身份不符都会失败。正式 CI 不接受手工文件参数覆盖选集；本地可用 `pnpm test:browser-e2e --file e2e/user-shell-navigation.spec.ts` 验证单个文件，本地回执不构成发布证明。

## 首次启用及权限

现有服务器网关尚不能接收新镜像协议，需要管理员执行一次受控安装。`scripts/prepare-stable-images-bootstrap.py` 从干净提交冻结发布器与哈希，生成本地入口；入口等待并核对精确主分支 CI，安全上传到 root 私有暂存目录，安装五项固定工具并验证当前线上服务。它不构建、迁移、创建标签或切换应用，同时可将已有闲置构建缓存降至约 2 GB。

完成首次安装后，日常版本及固定发布工具更新都由同一个手动 Workflow 完成，无需再次运行终端构建或 sudo 命令。服务器凭据轮换、主机重装或超出固定工具范围的运维变更仍是单独的管理员操作。

受限网关仅接受固定格式的状态、工具更新和发布命令，不开放远程 Shell。工具更新只安装精确主分支与成功 CI 对应的五项 Git blob，持同一发布锁、校验文件权限、网关最后启用，失败时恢复原工具文件。历史 1.0.4 来源回执协调代码只用于兼容已发生事件，不参与正常发布。

镜像拉取使用该次 Workflow 的临时 `GITHUB_TOKEN`（`packages: read`、`actions: read`）。凭据通过 SSH 标准输入传输，不放入参数或日志；临时 Docker 登录目录在拉取后删除，不新增永久 registry 密码。

## 镜像与缓存保留

健康验收和成功回执之后，保留当前及上一版本的应用/Worker/迁移镜像，以及任何容器仍引用的镜像；仅删除更早且属于本应用的无引用镜像，不使用强制删除。默认 BuildKit 的闲置缓存目标为约 2 GB。清理失败会记录维护提示，健康服务和成功回执保持有效。

正式发布的镜像清理复用归属、版本边界和容器引用分类，冻结当次项目镜像 ID 范围；每次仅按完整 ID 执行 `image rm --no-prune`，不回退到标签，不删除父镜像。删除前后验证全部镜像/容器、当前及上一版本、数据卷、配置、数据库账本和健康；新出现、变化或受引用的镜像不纳入删除，保护快照漂移即停止。逐项保留原因和实际删除 ID 写入部署日志与服务器审计。

每次镜像删除前必须先成功保存 root 私有意图审计；异常后补只读 ID 库存，分别记录确认删除、引擎保留及结果未确认的请求，失败审计同时输出安全部署日志。缓存部分失败的尝试 ID 和固定原因码单独保存为 `clean-failure.json`，不被最终复查覆盖；不能将尝试次数当作删除数量。

后续源码修复兼容 containerd 将摘要拉取引用同时放入 `RepoTags` 的形式：仅接受可信项目来源、明确 GHCR 仓库、与 `RepoDigests` 完全一致且摘要等于当前不可变镜像 ID 的引用；额外别名、其他仓库、摘要不符或标签异常仍保留。该兼容修复由真实发布回执的元数据指纹回归验证，随下一次正式发布更新工具后生效，不代表已删除历史镜像。

每次已验收的发布（含相同版本重试）都会通过既有受限缓存入口串行执行检查、必要的安全清理和最终复查，不再调用无 ID 范围的缓存 prune。低于目标时只检查；高于目标且没有可回收记录时直接保留并列出原因。`production-release-cache-maintenance` 产物保存检查、清理、最终库存和目标报告，保留 30 天；Runner 临时 SSH 身份单独存放并始终清理。Node 堆限制为 512 MB。

超额报告为 `exceeded` 并产生明确警告，列出不可回收记录与尚可回收记录的不同原因；不为压到 2 GB 破坏保护边界。维护失败为 `unverified`，不能宣称达标，也不会停掉已通过验收的应用；检查失败、超额原因与健康发布结果分别保留。

常规发布不执行宽泛 `system prune`、容器/卷清理或业务目录删除。指定旧版容器维护只删除上文两个固定且再次验证的容器；数据卷、数据库、用户文件、历史备份及其他应用镜像不会清理。

## 验收边界

迁移清单只允许保持不变或追加，已有名称、排序和 SQL 哈希必须保留。切换前失败尝试恢复精确源服务；迁移或目标写入启动后失败会停写并报告维护需要，不冒充发布成功。已完成版本可核对回执、账本和健康后幂等返回。

代码、CI 镜像、生产切换及真实外部短信/模型服务是不同证据。CI 的隔离验证不调用真实模型或短信；生产验收以精确镜像、数据库/Worker 和公网 `/api/health` 为准。
