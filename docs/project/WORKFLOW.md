# AI Project OS 项目工作流

本规范定义项目目标、里程碑、需求、任务、缺陷、验收证据和发布版本之间的关系，以及中途变更的处理方法。项目状态只在[任务总台账](TASKS.md)维护；本规范不替代应用仓库的安全、风险验证和发布约定。

流程关系见 [架构图](FLOW-ARCHITECTURE.md)；本文件和各权威规范定义实际门槛，图中不维护任务状态。

## 记录结构

保持一条可追溯链：

`项目目标 → 里程碑 → 需求/变更 → 执行任务 → 缺陷 → 验收证据 → 候选 SHA/镜像 → 发布回执`

| 记录 | 唯一事实来源 |
| --- | --- |
| 项目目标、阶段和汇总进度 | [项目总览](README.md) |
| 已有能力、历史交付内容与原版本证据 | [完成记录](DELIVERED.md)；只记录交付事实，不复制当前任务状态 |
| 功能模块职责、数据归属、上下游与交接合同 | [模块边界](MODULE-BOUNDARIES.md)；实际接收结果仍记 T/A/E |
| 当前任务/问题状态、负责人、优先级、阻塞和下一步 | [任务总台账](TASKS.md) |
| 状态变化、关键动作、阻塞、取消、合并、验收与更正的历史 | [执行日志](ACTIVITY.md)，追加记录，不复制当前状态 |
| 中途新增、删除或变更的决策及其影响 | [变更日志](CHANGES.md) |
| 当前产品需求基线和已知能力边界 | [PRD 基线](PRD.md) |
| 用户纠正、复发问题模式和预防规则 | [复发问题记录](LESSONS.md)；执行和缺陷状态仍引用任务 |
| 当前有效及待确认的原型、视觉和交互基线 | [设计基线](DESIGN.md) |
| 页面与待验状态的检查范围 | [UI 清单](UI-INVENTORY.md) |
| 测试、验收、发布和生产回执索引 | [证据索引](EVIDENCE.md) |
| 各阶段验收门槛 | [验收标准](ACCEPTANCE.md) |

任务总台账放状态，不在 PRD、变更日志和证据索引中复制另一份状态。重要讨论在作出决定后记入对应来源文件；尚未决定的内容保留为“待评估”。

## 所有任务与问题的追溯规则

范围覆盖需求、调查、设计、开发、测试、文档、代码同步、发布/运维及临时插单。每个实质工作在执行前建立或关联 T 编号；属于同一目标的小步骤可记录在既有任务下，不为每条工具命令制造任务。纯解释答复若形成决定、新问题、范围或承诺，当轮记入相应 C/T/L/E 或日志；没有新决定的重复答复无需造任务。

任何问题被用户提出、测试发现、审查发现或线上发现，当轮先登记问题 T 编号、原话/来源、记录日期、受影响范围、处理归属和下一步；未复现时注明“用户报告/待复现”，不能写成根因已确认，也不能等用户补全才记录。相同表象可能有不同根因，核实后才合并。

最小追溯链为 `来源 → 需求/决定 → T 任务或问题 → 执行动作与产物 → 用例/检查 → E 证据 → 验收结论 → 发布/观察（适用时）`。重复问题再关联 L 记录与原事件。每个节点必须有实际位置/编号；不适用写原因，没有提交或发布就保留“未提交/未发布”，不虚构 PR、SHA 或回执。

- 开工前：目标、来源、责任、范围、验收、依赖、风险和检查预算齐备；TASKS 标记进行中并在 ACTIVITY 记录开工。
- 执行中：关键决定、修改产物、失败、阻塞/解除、插单/恢复、范围变化及状态变化追加日志；记录实际日期和操作者。失败记录不得被成功重试覆盖。
- 转待验收：列产物、实际检查与结果、未验证项；若在代码工作区尚未提交，记录基准 SHA 和实际文件/补丁，不用基准 SHA 冒充变更已包含在提交中。
- 通过：验收者按目标核对并关联 E 证据，再更新当前状态；修复问题还需复现/预期、处理结果、相关回归和适用的 L 检查。发布证据另记，不由代码完成推导上线。
- 取消/延期/重复：保留编号、原因、决定来源和恢复条件/归并去向；重复条目取消并双向引用主条目，无法复现保留环境与尝试，不写“已修复”。
- 更正/复发：日志追加更正，引用旧事件；证据否定旧验收时记录重开原因，否则新问题建新任务并关联历史。不改写旧结论让历史看起来从未失败。
- 收工/交接：写明本轮完成、未完成、阻塞和下一步，更新总览。无记录的工作不能计为交付完成，无归属的问题不能隐去。

任务与问题共用 T 编号和唯一状态；问题报告与其调查/实现任务通过关联字段区分，同一修复工作不重复累计工作量。严重程度依据影响评估，优先级依据处理顺序；待复现不等于等待用户。历史补录标明“依据当前证据补录”，不倒填未知的时间、执行者和流程。

现阶段为仓库文档流程，没有新增不可篡改审计系统或自动 CI 门禁。Git 仅保存实际提交后的历史；未提交文档不会自动同步到其他工作区，交接必须显式说明。

## 模块与阶段交接

所有功能任务按 [MODULE-BOUNDARIES](MODULE-BOUNDARIES.md) 关联 F-001～F-012。任务开工明确实际交付者/接收者、源/目标模块、输入输出、数据和状态权威、依赖及异常责任；数据字段与状态机直接引用现有接口/服务合同，不另建互相漂移的副本。新增或修改合同须记录 C、消费者和证据影响。

交付使用 [交接模板](TEMPLATES.md)，绑定精确源码/设计版本或未提交文件哈希。接收方核对前置、产物、定向结果及遗留，追加接受/拒收事件；同一执行者承担两种职责也须分清证据范围。无明确接收方由主代理认领协调，不自动推给用户。

上游单模块通过、下游集成通过和整个功能通过分开记录；上传、解析、审核、索引、问答、计划和发布各自有状态权威。合同不符退产出方，合法输出消费错误归接收方，争议由主代理根据复现证据归属；不能静默补写数据或改语义。拒收/暂停/恢复按既有 T 状态及 A 事件保留，不抹去失败历史。

阶段可合并执行，职责和接收条件不能省略；详见模块文档的十阶段交接表和 ACCEPTANCE。此约定不额外要求用户逐阶段审批，也不授权业务/生产动作。

## 问题驱动的边界改进

按 [LESSONS](LESSONS.md) 的持续改进规则执行：问题登记 → 四类边界核定 → 升级评估 → 修复与预防任务 → 规范/合同/检查变更 → E 复验与接收 → 下次适用交付复核。复发、共同组件/跨模块、验收后漏测、高风险及重复修复失败分别有升级去向；主代理协调，实际执行责任留在 T。

变更合同/标准时登记 C，保留前后差异、消费者和证据失效范围；局部修复未改合同则直接引用现有规范。必需预防属于本次验收，可分离的后续观察有明确关联 T 和触发点；不新增平行改进台账。每次修复、下一次适用变更和发布准备核对改进效果，未观察或未验证如实标明。

## 工作阶段

阶段的产物及通过条件见[阶段验收标准](ACCEPTANCE.md)。阶段可以按任务规模合并执行，但依赖顺序和通过条件仍然成立。

| 阶段 | 主要产物 | 完成并转入下一阶段的条件 |
| --- | --- | --- |
| 1. 立项 | 目标、问题、范围、优先级、边界 | 目标可观察，初始责任人与工作入口明确 |
| 2. 需求 | PRD、用户流程、异常和验收场景 | 业务规则和验收范围清楚 |
| 3. 原型与设计 | 批准的原型、视觉规范、页面和状态清单 | 关键流程及展示状态已检查；设计边界明确 |
| 4. 技术方案与拆分 | 依赖、接口或数据影响、风险、任务卡 | 未知已核实，任务可独立执行和验收 |
| 5. 实现 | 对应任务产物和开发自检证据 | 行为符合需求和设计；代码边界明确 |
| 6. 测试 | 受影响范围的测试和缺陷记录 | 目标场景通过，跳过与模拟部分已说明 |
| 7. 产品/设计验收 | 对照需求和批准设计的操作及视觉结果 | 关键流程、页面、状态及对齐规则通过 |
| 8. 发布准备 | 候选 SHA、镜像身份、适用 CI、迁移与回退评估 | 候选身份和验收证据一致；风险未决项有处理结论 |
| 9. 上线 | 精确发布回执、健康检查、版本身份 | 用户在指定 Workflow 发起，发布条件成立 |
| 10. 上线观察 | 核心流程结果、问题与后续任务 | 观察结果已记录；新缺陷与待办有归属 |

只有验收范围内的已确认需求才计入“当前承诺范围”。建议、想法、历史计划和尚未评审的变更属于待评估，不得用于承诺进度或宣称产品现有能力。产品或设计任务可以在已验收后关闭，不需要虚构发布步骤。

## 任务状态与进度

任务状态只使用：`待澄清`、`待开始`、`进行中`、`待验收`、`已验收`、`已取消`。优先级用 `P0` 阻断、`P1` 当前里程碑、`P2` 常规、`P3` 有空再做；临时需求不会自动变为 P0。

阻塞是独立字段，不是可替代任务状态的“进行中”。阻塞任务仍保留原状态，并记录阻塞原因、等待对象、解除条件、暂停位置和恢复后的第一步。取消任务要记录来源或原因，不能静默删除。

任务进入 `进行中` 前必须有明确目标、范围、验收条件、依赖、执行者和下一步。执行中发现范围变化时，先登记变更并评估影响；确认在现有授权范围后更新任务和相关 PRD/设计，再继续。`待验收` 要附可打开的证据，验收者按条件核对；失败回到 `进行中` 并关联缺陷，全部条件通过才转为 `已验收`。

主总览分别报告当前承诺范围内的任务状态、里程碑门槛、阻断缺陷、已验收证据和发布状态。完成数按任务数和里程碑阶段汇总；范围增加、移除或拆分时记录分母变化及原因。没有明确、稳定的权重时不报单一完成百分比。以下概念不能混为一个进度：开发中、已验收、已发布、生产已验证。

主任务默认同时推进一个；仅在依赖清楚、执行对象真正独立且不会破坏验收或协作时并行。待开始任务按优先级和依赖排序；被阻塞任务必须保持可见，不能计作完成。任务按目录与实际活动仓库标明工作位置。项目管理文档保存在应用仓库的 `docs/project/`，与源码一起版本化；每个 Git 工作区使用本分支内的文档，不通过绝对路径共享可变台账。新工作区必须基于已包含这些文档的提交，或显式迁移对应未提交文档，不能静默建立第二套台账。应用变更须在经核实的应用工作区进行，不把过期分支、备份或 detached worktree 当作当前主线。

## 临时需求与范围变更

新增想法先进入[变更日志](CHANGES.md)，决定纳入的工作进入[TASKS.md](TASKS.md)。也可建立明确标为“待澄清、范围外”的调查任务，但不得计入已承诺范围或提前实施。分类如下：

- 对现有行为或要求的补充：更新相应 PRD/设计和验收条件，注明前后差异。
- 不符合已接受标准的结果：登记缺陷并关联原需求、实现任务及受影响版本。
- 独立的新能力：登记新需求；确认范围和目标版本后再建执行任务。
- 紧急插单：记录原因、优先级、被暂停/延后任务及恢复点。
- 待探讨想法：保持待评估状态，不加入承诺范围，不自动开始实现。

每项范围变更走 `登记 → 说明目标和缘由 → 评估设计/技术/测试/工期/依赖影响 → 确认优先级及纳入范围 → 更新唯一规范来源和进度分母 → 建立或更新任务 → 实现和验收`。影响排期或关键业务规则时提交明确选项及影响供用户决定。其他事项按已有授权继续处理。来源消息或日期无法确定时写明“待补”，不补造。

新增要求不能消除对原计划的追踪。被打断的任务在 TASKS.md 保留已完成范围、待办、暂停原因、恢复条件及下一步。原型、PRD 和验收规则之间有冲突时记录决定后更新对应权威文件；不能一边按新要求实现，一边留存旧标准声称已通过。

## 复发问题的持续记录

原型、UI/UX、前端和验收工作在开工时读取 [LESSONS](LESSONS.md)，在任务卡列适用 L 编号、受影响组件/页面/状态和检查计划；无需等待用户再次提醒。设计修订优先级以 DESIGN 为准，旧教训中的规则被新决定替代时保留历史并标明替代关系。

收到重复问题反馈，当轮先追加事实与来源，绑定原问题模式和执行任务。根因未明明确写待查；修复后补实际根因、同类使用方检查、回归位置及证据。无法自动化的视觉判断保留可重复审阅步骤和实际审阅结果，不能用截图生成替代。

交付按命中条目逐项写结果和候选。没有有效回归或审阅证据，不能宣称防复发完成；问题再次出现时检查旧用例漏场景、断言、执行和基准有效性。新缺陷建新任务；只有证据否定旧验收时才重开原任务。历史事件保留，不把未复现的用户报告转成已证实根因。

项目规则和事件保存在本仓库；个人长期记忆只保存用户明确要求及入口。新工作区须包含对应文档版本，未提交文件不会自动出现在远端或其他工作区；交接必须说明这一点。本规则不新增产品内自动记忆、CI 检查或应用数据库写入能力。

## 责任与持续更新

- 用户决定目标、关键业务/视觉取舍和正式发布；不需要为已授权范围内的每个常规步骤再确认。
- 主代理负责维护项目与任务台账、识别影响和风险、组织交付，不能把推测写成事实或把局部检查报告成全量通过。
- 执行者在开始、阻塞、转验收、完成或交接时更新其任务状态、产物、验证和下一步。验收者记录通过条件及证据，必要时由独立人员进行高风险审查。

每轮工作开始，先查项目总览、当前台账、最近变更及适用的 AGENTS.md；涉及产品行为或视觉时再读对应 PRD/设计。收工前更新台账和证据索引，写清已完成和未完成项。新能力验收后更新 DELIVERED 对应能力及总览，正式发布后追加精确版本和回执；历史任务资料不全时只回填有依据的交付事实，不补造完成日期或验收人。记录证据使用仓库路径、SHA、CI 运行身份、版本、环境、检查命令及结果；引用不变的成功证据时核对输入、候选、工具和配置仍匹配。候选 SHA、规范、运行器、选集或依赖条件改变时，受影响的旧验收不能作为新候选的直接证明。

应用安全、验证、提交和发布以当前应用仓库的 `AGENTS.md` 与 CI 为准。此套项目治理不放宽凭据、数据库、生产或外部通信的限制，也不授权 commit、push、merge、发布或部署。发布仍需用户依照应用既有流程手动触发。
