# v1.0.5 — 修复发布权限与恢复来源回执

本文件描述待验证候选。`v1.0.4` 标签保持原提交；该次正式 Workflow 因 Nginx 配置权限校验失败而停止，随后完成了受控运行态恢复。当前生产实际版本和健康以 `/api/health` 为准，运行态恢复不等同于正式 Workflow 发布完成。

## 本版本变更

- Nginx 目标配置和迁移前回退配置使用显式设置权限、同步文件与目录的原子安装流程。在私有 `umask` 下仍保持 `0644`，避免权限校验再次触发保护停机。
- 增加限定于已核实 `v1.0.4` 恢复事件的来源回执协调。核对 root 管理的恢复记录、精确 Git 标签与提交、容器和镜像、146 条数据库账本、当前配置与本机/公网健康，以及原升级前备份后，保留旧回执并写入明确标识的恢复回执。
- 恢复来源校验读取备份脚本实际生成的七字段 COS 标记，核对校验文件对象、验证时间及原有对象和哈希证据，避免合法备份被字段数量误判。回归测试直接执行备份脚本的标记生成代码。
- 恢复回执记录当前运行态和原 `v1.0.0` 升级前备份，不将当前数据库快照或不完整的历史配置证据冒充迁移前快照，也不宣称原失败 Workflow 或 GitHub Release 已成功。
- 工具维护先验证候选源码、精确同 SHA 的成功主分支 CI 与实际生产来源，随后协调回执并更新固定的五项发布工具。安装失败时回滚旧工具、工具状态和本次协调前的回执；若进程中断，下次维护仅允许从已验证的原提交与候选提交文件继续安装，未知字节拒绝继续。该维护不构建应用、不迁移数据库、不停止或切换现有服务、不触发正式发布。

本次未新增数据库迁移，相对当前已恢复的 `1.0.4` 仍为 146 条。

## 发布与验证边界

代码和精确同 SHA CI 通过后，先完成一次受控的回执协调及发布工具升级。此后由用户在 **发布正式版本** 选择 `main` 手动发布 `1.0.5`；正式 Workflow 核验工具哈希、复用同 SHA CI，并按高风险发布策略核对备份、账本和目标健康。生产发布继续跳过隔离恢复演练。

代码检查、工具维护、运行态恢复和正式发布分别记录证据。未经用户点击 Workflow，不自动发布；真实模型调用、短信、文件上传和业务写入不在本次发布工具修复的现场验收范围内。
