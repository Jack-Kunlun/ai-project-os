# AI Project OS 分阶段验收标准

每一阶段只在其可观察条件满足且证据挂到对应任务后通过。未涉及的项目标记“不适用”；没有运行的检查不得写通过。任务状态和结果统一记录在[任务总台账](TASKS.md)，证据详情统一链接至[证据索引](EVIDENCE.md)。

## 每项任务与问题的记录门槛

按 [工作流](WORKFLOW.md) 核对：T 编号、原始来源、处理归属、验收条件、关键事件日志、实际产物及 E 证据可互相追踪；不适用项有说明。没有证据不得标“已验收”；取消/重复/无法复现必须留原因与处理结论，不能记为修复成功。

发现新问题当轮入账；已有问题不能只从列表删除。记录过程不足的历史事项可据现有证据补录，并注明缺失，不以本轮文档验收补造过去的完整过程。

## 功能模块与交接门槛

受影响 F 模块、实际交付/接收责任、输入输出、数据/状态权威、合同与候选版本、异常和恢复责任必须明确，详见 [MODULE-BOUNDARIES](MODULE-BOUNDARIES.md)。有跨模块影响时核对其边界检查行，关联实际用例/检查与 E 证据；不适用说明原因。未知/待审/已排队/部分成功不能计作下游完成。

接收者必须留下结论和依据。上游单元或合同检查通过只支持其范围；功能验收还需要适用的消费方和端到端结果。设计→组件→页面须有样式、间距归属和状态对照；服务→UI 须核对真实业务状态；验收→发布须绑定同一候选。违反现有授权、安全或数据边界的情况不能靠风险备注放行。

拒收后登记问题 T、责任及恢复条件，原交付任务按失败处理回到进行中或保留阻塞；合同变化先记 C 并更新受影响消费者。缺少交接证据不得标“功能已交付”。本轮 T-028 只验收文档，不表示本表业务场景已执行。

## 需求立项

**通过：** 问题和目标具体；预期结果可观察；当前范围、非目标、用户和环境约束、优先级、依赖和主要风险有记录；初始验收范围有归属。主观体验要求已具体化为可检查的行为或设计原则。

**失败处理：** 涉及目标或范围的关键条件不清时保持“待澄清”，记录问题与影响；不以猜测扩展承诺。

## PRD 与业务流程

**通过：** 用户角色、前置条件、正向流程、主要边界、失败恢复、持久化结果和权限边界都有对应场景；需求能追溯到验收条件；未实现能力明确标为设想或未开放。核心歧义已有决策记录。

**失败处理：** 发现流程或数据状态缺失时先补 PRD；由新事实改变既有需求时创建变更记录并说明受影响任务和验收条件。

## 原型与视觉设计

**通过：** 视觉和交互基准有明确版本或提交，关键路径可走通；涉及的页面、公共组件、操作界面和代表状态已列入[UI 清单](UI-INVENTORY.md)。对全站视觉改版，还需覆盖页面 × 交互状态 × 主题/语言 × 视口的约定组合；每页至少有桌面和窄屏代表结果，语言/主题只在产品支持且变更受影响时增加对应组合。清单注明真实用户数据区域与不可预测区域。

**通过方式：** 在可运行原型或设计预览中走通交互，审阅相应状态，核对文本基线、字段和控件边缘、表格列与表头、行间距、长文本换行、按钮组及错误/加载布局；模拟数据与能力必须明确标识。此阶段不要求尚未开发的真实应用已可运行。实现后再用精确候选应用对照已确认设计做产品与设计验收。截图差异可定位变化，需由验收者判断是否符合基准；不得把有已知偏差的当前页面直接设为正确基准。

**失败处理：** 设计冲突或缺少关键状态时回到 PRD/设计；UI 清单未覆盖的页面不能被整体验收结果代替。

## 技术方案与任务拆分

**通过：** 影响的代码、页面、依赖、数据、权限、外发、构建/部署和现有工作已识别；方案约束、任务次序和非目标清楚；每项工作有负责人、依赖、验收条件、风险分类及最小验证方法。潜在高风险或架构未知在实现前解决或明确升级处理。

**失败处理：** 未明白的公开接口、权限、数据迁移或跨仓库影响转为研究事项；不让执行者以猜测决定安全或业务规则。

## 开发实现

**通过：** 变更满足对应 PRD 和批准设计；保留未授权范围内的现有行为与用户改动；有聚焦的功能测试或自检，复用已有的、仍匹配的验证证据，并在台账中记录文件及检查结果。全站 UI 迁移按组件和清单逐项完成，不以修改一组公共 CSS 代替页面确认。

**失败处理：** 复现未满足条件时登记缺陷，补上可观察的验收条件；需求或设计已变化时先登记变更。

## 测试与缺陷修复

测试报告分别说明检查了什么、对哪个候选、结果以及范围边界：

- **源码/合同检查：** 证明受检查的代码或配置符合静态约束，不能单独证明实际界面和用户流程正确。
- **行为测试：** 对功能输入、输出、边界、错误处理和可恢复结果做断言；重要业务闭环需要实际执行，而不是只检查相关文本存在。
- **数据库/集成测试：** 仅在隔离数据库和指定集成环境证明被实际执行的持久化、事务、权限和并发路径。跳过用例另列。
- **浏览器与视觉检查：** 对受影响页面完成真实交互、状态和几何检查；记录视口、语言、主题和候选版本。截图生成本身不算人工视觉验收。
- **外部现场验证：** 只在真实目标服务及部署中发生的检查可标为现场验证；本地 mock、录制响应和 CI fake 不能替代它。

**通过：** 计划内必需检查均有通过回执；失败已修复并复验；以 `skip`、`mock` 或 `unverified` 呈现未实际证明的场景。保留尝试结果，重试后通过的 flaky 用例单独记录并调查，不抹去间歇失败。

**失败处理：** 缺陷需有复现路径、预期/实际结果、影响和优先级。修复后重跑失败用例及直接相关回归；缺陷由验收者在复验通过后关闭。

## 复发问题检查

涉及原型/UI/UX/前端的任务，验收记录必须列出 [LESSONS](LESSONS.md) 命中条目、适用页面/状态、候选与实际结果。明确违反当前批准设计的错位、间距缺失、遮挡等问题未关闭，受影响项不得通过；未检查或测量跳过不能计为通过。

已复现且本次修复的重复缺陷必须完成同类使用方检查，并有能识别原错误的自动回归或可重复视觉审阅及证据。再次出现时记录旧防线未生效的原因及补救，不只重做局部修复。写入复发问题文档只完成记录，不等于回归实现或问题关闭。

## 问题边界改进的接收

每个实际修复核对 [LESSONS](LESSONS.md) 的发生/影响/责任/验证边界、实现根因与漏检原因、升级决定、命中 F/L、必要的规范/用例变更以及同类使用方证据。未查清的原因或未验证范围必须保留，不能写成系统性问题已消除。

本次必需预防与复验未过，原修复不得最终验收；如果后续观察可单独交付，必须关联负责人明确的 T，记录触发时点和接收条件，不能借观察任务转移本次必要检查。新增回归应有识别原错误的证据，无法获得时说明验证边界；未来没有复发只在实际观察范围内成立。

边界/规则升级须有前后差异、依据、消费者和被替代范围；变更后重新核对受影响证据。按高风险规则处理安全/数据/外发等信号，不能以一般风险接受豁免强制约束。文档机制验收与实际改进效果验收分开记录。

## 产品与设计验收

**通过：** 验收者按 PRD 场景实际操作候选版本并核对结果；UI/交互变化逐项对照当前批准设计及 UI 清单；记录构建/环境和证据链接。明确列出阻断问题及待验证项。UI 整体改版需逐项完成适用页面和代表状态，页面未检查不得宣告全站迁移完成。

**失败处理：** 行为不符回到实现/需求；视觉或文本对齐不符回到设计/实现；发现设计本身有误先更新规范和批准基准，再进行新的对照验收。不能修改基准来掩盖缺陷。

## 发布准备

**通过：** 候选 SHA、版本、CI 结果和将交付的不可变镜像身份相符；CI 按实际生产源版本至候选的累计影响执行适用范围；阻断项已关闭，非阻断遗留有明确处置及风险决定；迁移变化经过适用的升级验证并评估恢复路径。验收证据链接到精确候选，而非仅按版本名复用不同提交的检查。安全/权限/数据保护等强制边界不因一般风险接受而被豁免。

**发布前最低记录：** 候选与源版本、适用风险级别、通过/失败/跳过/模拟/未验证清单、迁移清单是否变化、发布责任及健康核对方式。常规应用版本依照应用仓库规则，不增加备份/恢复要求；涉及数据库或不可逆变更时按其风险单独验收。

**失败处理：** CI 与生产源、候选 SHA、镜像或适用风险证明身份不符时停止发布，补齐与精确候选一致的证明后再进入发布。

## 发布上线与观察

**通过：** 用户通过既有手动 Workflow 发起发布；应用仓库回执确认实际交付身份。上线后核对 app/Worker/数据库和版本健康、适用的关键用户流程以及相关外部服务边界；记录健康证据及任何未现场核验项。运行期间发现的缺陷或需求作为关联任务纳入台账。

**失败处理：** 发布身份不符或健康失败依照既有生产规程停止/处理；未获得上线回执不能标记已发布，只有公网/目标环境相应证据成立才标记生产已验证。

## 验证范围与安全边界

针对应用实现时，沿用应用工作区适用的 `AGENTS.md`、累计风险分类及 CI 选测规则：

| 风险 | 验证原则 |
| --- | --- |
| 低 | 仅检查受影响的文档/样式/静态产物；按所属仓库约定执行直接检查。 |
| 中 | 执行受影响功能测试和该影响面必需的浏览器/无障碍检查；需要时做一个受影响模块验证。 |
| 高 | 对认证、授权、额度、数据、外发、迁移、依赖、CI/CD、生产工具及未知影响运行应用约定的完整适用门禁；完成后进行一次独立审查。 |

失败、覆盖计划不能证明所涉页面/业务、影响面扩大或所选 CI 策略本身发生变化时，按应用约定扩大检查；不默认重复已在相同输入、工具、环境和候选上通过的证据。只修改本目录的项目台账或流程说明，做链接、状态引用和文件差异检查即可，不运行产品构建或业务套件。

此文件不得弱化应用仓库的凭据、生产、提交、发布或恢复规则。相关规范见[应用仓库约定](../../AGENTS.md)、[CI 与浏览器门禁](../../docs/continuous-integration.md)及[正式发布流程](../../docs/production-release.md)。这些链接均在本仓库内解析；换分支时核对该提交的规范和文档是否齐全，不用其他临时工作区的路径代替。
