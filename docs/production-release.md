# 正式版本发布

GitHub Actions 只保留 **CI** 和 **发布正式版本**。用户在「发布正式版本」点击 **Run workflow**、选择 `main`；代码提交和 CI 成功不会自动发布生产。

## 日常发布

1. 将改动、递增的 `MAJOR.MINOR.PATCH` 版本及对应说明提交到 `main`。
2. CI 按当前生产源版本到该 SHA 的累计差异选择测试，构建一次共享镜像图，使用同一镜像验证浏览器、性能与受影响的隔离候选，然后发布不可变摘要镜像和 `release-images` 清单。
3. 点击「发布正式版本」。工作流核对精确 SHA 的成功 CI 及实际源版本证明，创建或复用 annotated 版本标签；生产作业再更新固定发布工具。
4. 生产校验 CI 运行、产物哈希、镜像摘要/ID、版本和源码 SHA，拉取已验证镜像，不构建源码。迁移清单未变时跳过迁移和权限协调；变化时执行已经 CI 验证的迁移。
5. 自动核对应用、Worker、数据库账本和公网健康。成功后写发布回执、发布 GitHub Release，并清理旧镜像和闲置构建缓存。

常规发布不创建或验证备份，不执行恢复演练。已有业务数据、数据卷、上传文件和历史备份保留。新回执使用 `release_protocol=stable-v2-images`、`backup=not-required restore=not-required`；历史回执继续兼容。

版本标签不可移动，必须为 annotated 且指向本次相同 SHA。主分支前进、生产来源改变、CI 证明不足或镜像清单过期时，发布会在切换前停止。重新运行精确提交的主分支 CI 后再点击发布，不重复标签全套测试。CI 产物保留 30 天。

## 首次启用及权限

现有服务器网关尚不能接收新镜像协议，需要管理员执行一次受控安装。`scripts/prepare-stable-images-bootstrap.py` 从干净提交冻结发布器与哈希，生成本地入口；入口等待并核对精确主分支 CI，安全上传到 root 私有暂存目录，安装五项固定工具并验证当前线上服务。它不构建、迁移、创建标签或切换应用，同时可将已有闲置构建缓存降至约 2 GB。

完成首次安装后，日常版本及固定发布工具更新都由同一个手动 Workflow 完成，无需再次运行终端构建或 sudo 命令。服务器凭据轮换、主机重装或超出固定工具范围的运维变更仍是单独的管理员操作。

受限网关仅接受固定格式的状态、工具更新和发布命令，不开放远程 Shell。工具更新只安装精确主分支与成功 CI 对应的五项 Git blob，持同一发布锁、校验文件权限、网关最后启用，失败时恢复原工具文件。历史 1.0.4 来源回执协调代码只用于兼容已发生事件，不参与正常发布。

镜像拉取使用该次 Workflow 的临时 `GITHUB_TOKEN`（`packages: read`、`actions: read`）。凭据通过 SSH 标准输入传输，不放入参数或日志；临时 Docker 登录目录在拉取后删除，不新增永久 registry 密码。

## 镜像与缓存保留

健康验收和成功回执之后，保留当前及上一版本的应用/Worker/迁移镜像，以及任何容器仍引用的镜像；仅删除更早且属于本应用的无引用镜像，不使用强制删除。默认 BuildKit 的闲置缓存目标为约 2 GB。清理失败会记录维护提示，健康服务和成功回执保持有效。

不执行宽泛 `system prune`、容器/卷清理或业务目录删除。数据卷、数据库、用户文件、历史备份及其他应用镜像不会清理。

## 验收边界

迁移清单只允许保持不变或追加，已有名称、排序和 SQL 哈希必须保留。切换前失败尝试恢复精确源服务；迁移或目标写入启动后失败会停写并报告维护需要，不冒充发布成功。已完成版本可核对回执、账本和健康后幂等返回。

代码、CI 镜像、生产切换及真实外部短信/模型服务是不同证据。CI 的隔离验证不调用真实模型或短信；生产验收以精确镜像、数据库/Worker 和公网 `/api/health` 为准。
