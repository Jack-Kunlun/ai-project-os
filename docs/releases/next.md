## v0.5.0-dev.1 历史生产基线：移除默认工作区 Owner 初始化

状态：已作为历史生产基线发布；当前 `.2` 升级候选不得改写或复用其 clean reset 语义。

此前 v0.4.x 在创建平台 `admin` 后，仍要求管理员另行创建默认工作区的业务 Owner，才允许普通用户使用 GitHub 登录；OIDC 也依赖这项全局初始化。平台管理账号与业务账号分离是合理的，但全局默认工作区及其人工 Owner 不符合“每位普通用户管理自己的个人工作区”的目标。

v0.5.x 的目标行为：

- 平台 `admin` 初始化后即可独立使用管理台；有效配置 GitHub OAuth 后，普通用户可以发起 GitHub 登录，无须先人工创建业务 Owner。
- 首次通过 GitHub 注册的普通用户获得自己的工作区，并成为该工作区的 Owner；不自动加入全局默认工作区，也不赋予平台 `admin` 工作区或项目权限。
- 用户、工作区、已确认的 Owner 成员关系、账户权益与审计证据必须在受控事务中一致建立；重复回调、并发注册和失败重试不得产生重复账号、工作区或孤立权限。
- 同邮箱已有本地账号时继续禁止静默合并，必须走显式绑定；OAuth 配置错误、回调验证失败和数据库写入失败仍要安全失败关闭。
- 登录页分别说明“平台管理员未初始化”“GitHub OAuth 未配置/无效”等真实原因，不再把缺少人工创建的业务 Owner 统称为“平台初始化尚未完成”。
- 移除默认工作区 Owner 的初始化页面、API 和服务端入口；OIDC 首次建号及管理员创建的本地普通用户也获得自己的个人工作区，加入其他工作区属于额外的成员关系。

当前按“没有普通用户”的空数据状态实施，不设计旧用户、旧会话或项目数据迁移。向前迁移只取消项目默认工作区数据库默认值、移除 `PlatformBootstrap` 的旧 Owner 初始化字段，并清除全新空库中的空默认工作区种子；不会执行用户数据搬迁或会话批量撤销。尚未执行生产迁移。

验收以全新数据库仅完成 `admin` 初始化为起点：GitHub 发起入口应可用；首次成功回调后新用户拥有自己的个人工作区且不自动加入历史默认空间；本地 `admin` 仍只能进入管理台；重复/并发回调、已有邮箱与失败回滚均有聚焦测试。OIDC 与本地新增普通用户也须在同一事务中获得个人工作区，同时保留经授权加入其他工作区的关系；旧 Owner 初始化入口不再可用。真实外部 GitHub/OIDC 授权与回调需在目标环境单独验收，自动化测试不能替代外部联调。
