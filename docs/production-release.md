# 正式版本发布

当前源码的正式发布入口为 GitHub Actions 中的 **发布正式版本**（[release-stable.yml](../.github/workflows/release-stable.yml)）。由用户点击 Run workflow 发起；提交代码和 CI 通过只产生验证结果，不自动发布生产。

工作流目录仅保留 `CI` 和 **发布正式版本**。旧版专用发布配置已移至[历史合同夹具](../test/fixtures/legacy-workflows/README.md)，不再执行。为移除旧 Actions 侧栏条目，五个旧工作流的运行元数据、日志及可用产物先导出至本地归档，再删除其 GitHub 运行记录；版本标签、GitHub Releases、CI 和正式发布工作流的运行记录保留。

## 日常发布

1. 将待发布代码、递增的正式版本号及对应版本说明合入 `main`。`package.json`、公开版本标识、OCI 镜像标签和版本说明必须一致，使用不含预发布后缀的 `MAJOR.MINOR.PATCH`。
2. 在 Actions 打开 **发布正式版本**，点击 **Run workflow**，选择 `main`。
3. 工作流复用该 SHA 已成功且覆盖实际生产来源与累计风险的主分支 CI，创建 annotated 版本标签，然后执行生产构建、停写备份、账本核对、服务切换及公网健康检查。生产发布不执行隔离恢复演练；高风险版本继续执行迁移和权限协调，低/中风险且迁移清单完全相同的版本跳过这两项。成功后才发布 GitHub Release。

日常发布不需要登录服务器或手动执行构建命令。版本标签不可移动；已存在的标签只能在类型为 annotated 且指向本次相同 SHA 时复用。标签指向其他提交时，须递增版本号后重新提交。等待验证期间主分支前进时，旧候选会停止，避免把已过期的候选切换到生产。

主分支 CI 按线上源版本到候选 SHA 的累计差异选择低、中、高风险门禁，具体检查见[持续集成](continuous-integration.md)。发布时核对同 SHA 的成功结果及其来源/风险证明，不重新跑完整标签 CI。人工推送标签时只做 annotated 类型、SHA 和主分支 CI 身份校验。生产来源变化导致已有证明不足时，流程会明确停止，重新运行该提交的主分支 CI 后再点击发布。

## 一次性通道接入

旧服务器的受限网关不能自行安装新的 root 发布工具。管理员首次接入永久通道时，核对已审查提交及其完整主分支 CI，通过固定哈希安装发布器、备份工具、产物检查器、sudoers 和网关。网关最后启用；安装失败时恢复原工具文件。

这一步只准备发布基础设施，不创建版本标签、不构建应用、不执行迁移、不切换服务。普通正式版本复用同一通道；发布工作流核对安装文件的实际哈希与候选中的相同工具文件，允许工具安装提交早于应用提交。主机工具内容发生变化时，流程会停止，须完成独立的运维升级。

仓库使用已有 `production` Environment、生产主机变量、SSH 私钥和固定 known_hosts。永久网关只允许状态查询及带明确版本、提交和确认常量的发布命令，不授予任意远程 Shell。

## 已恢复服务的来源回执协调

`v1.0.4` 的 146 条迁移与运行态恢复已经独立核实，原正式 Workflow 仍失败，旧 `last-deployment` 仍指向 `v1.0.0`。这类状态不能仅凭健康接口改写为普通发布成功，也不能将旧回执直接用于下一次发布。

该事件的受控工具升级会先验证精确候选源码及主分支 CI，再持发布锁核对 root 管理的恢复记录、标签与提交、完整账本、精确容器/镜像身份、配置和实时健康，以及对应的原升级前备份。验证完成后保留旧回执，写入独立类型的 `RECOVERY_OK` 来源回执，标记 `release_protocol=stable-v1-recovery`，再升级固定发布工具。验证不通过时不协调回执；若工具安装失败，恢复旧工具、状态文件及本次改写前的精确回执字节，已保存的历史回执仍保留。进程中断后的重试只接受分别匹配原 `b56` 或精确候选提交的工具文件，以及与这两个提交之一完全匹配的可信工具状态；出现未知字节时拒绝继续。维护不构建、迁移或切换应用。

恢复回执仅证明已核实的 `v1.0.4` 可以作为下一前进版本的来源，不表示原 Workflow 或 GitHub Release 成功。它区分当前运行态快照与原 `v1.0.0` 升级前备份，不虚构缺失的迁移前数据库快照或完整配置哈希。正式发布成功仍由后续用户手动发起的 Workflow 回执及目标公网健康共同确认。

## 数据和失败边界

发布只接受前进的正式版本。迁移可保持不变或追加新条目，已有迁移名称、排序与 SQL 哈希必须保留。备份包含数据库、主密钥、上传文件及受保护主机配置；每次发布都核验异地备份。生产发布按当前策略跳过隔离恢复演练，不以演练结果作为生产切换条件。高风险版本仍执行生产迁移、权限协调和目标账本验证，回执使用 `restore=skipped-by-policy-<源迁移数>-to-<目标迁移数>` 记录跳过原因与迁移范围。低/中风险且迁移清单完全相同时，不运行迁移和权限协调，回执记录 `restore=not-required`。历史已执行演练的发布回执仍可用于同版本幂等核验。

迁移尝试前失败时恢复精确源版本；迁移尝试后失败时保持停写，等待按备份证据恢复，不自动启动旧写入服务。已完成的同一版本可核验回执、账本和健康状态后幂等返回，不重复迁移。

跳过发布时的隔离演练意味着本次生产备份未通过完整恢复与升级演练，备份工件和异地副本仍需校验。CI 的隔离数据库与 Compose 候选验证继续保留。历史 `ai-project-os-restore` CLI 尚不支持 1.x 正式版本；生产迁移后的灾难恢复仍需管理员依据本次备份处理，不能直接套用旧 CLI。

成功 CI、工具安装、发布回执和公网健康是不同证据，检查各自负责的边界，不重复整套代码验收。只有工作流取得目标版本的发布成功回执，且 `/api/health` 的版本、数据库和 Worker 均符合预期，才表示生产切换完成。真实短信、模型、Git、OIDC 等外部服务的现场验收单独记录。
